# Technical Design Template

Copy this structure when generating a technical design document. All sections are required unless explicitly marked optional.

---

```markdown
## Technical Design: [Feature Name]

**Proposal:** [OpenSpec proposal ID / link, or "N/A — no openspec"]  
**Status:** Draft | In Review | Approved  
**Author:** [AI-generated, reviewed by: name]  
**Date:** [YYYY-MM-DD]  
**Prior art:** [List relevant existing designs found, or "None identified"]

---

### 1. Problem Summary

[1-2 paragraphs: what user or system problem does this solve, and why is now the right time?
Do NOT restate the proposal verbatim — synthesize it.]

---

### 2. Proposed Solution

[Core approach in 2-4 sentences before diving into details. A reader should understand
the general strategy without reading the full doc.]

---

### 3. Affected Components

List every module, service, or layer that this change touches:

| Component | Change Type | Description |
|-----------|-------------|-------------|
| [module/service name] | New / Modified / Deleted | [What changes and why] |

---

### 4. Interface Design

#### New or Modified APIs

```
[HTTP method] [path]
Request:  { field: type, ... }
Response: { field: type, ... }
Errors:   [error code]: [condition]
```

#### Events / Messages (if applicable)

```
Topic: [topic name]
Payload: { field: type, ... }
Producer: [module]
Consumers: [module list]
```

#### Internal Interfaces / Contracts (if applicable)

[Describe cross-module or cross-layer contracts introduced or changed]

---

### 5. Data Model

#### New Entities / Tables

| Field | Type | Nullable | Description |
|-------|------|----------|-------------|
| id | UUID | No | Primary key |
| ... | ... | ... | ... |

#### Modified Entities

[List fields added, removed, or changed. Note migration implications.]

#### Data Flow

[Describe how data moves through the system for the main use case.
Use ASCII diagram if helpful.]

```
User → API → [ServiceA] → DB
                       → [EventBus] → [ServiceB]
```

---

### 6. Options Considered

[Required when multiple approaches were viable. Omit only if there was genuinely one reasonable option.]

| Option | Approach | Pros | Cons | Decision |
|--------|----------|------|------|----------|
| A (chosen) | ... | ... | ... | Chosen because... |
| B | ... | ... | ... | Rejected because... |

---

### 7. Reused from Prior Art

[List specific utilities, patterns, or components being reused from existing code.]

| Reused Element | Source | How Used |
|----------------|--------|---------|
| [ClassName / utility] | [file path or design doc] | [how it's applied here] |

If nothing is reused: state "No reusable elements identified — this is new territory."

---

### 8. Open Questions

[Items that require a human decision before implementation can proceed.]

- [ ] [Question] — needed before: [which implementation step]
- [ ] [Question] — impact if deferred: [what breaks or gets harder]

If none: "No open questions. Design is ready for implementation."

---

### 9. Impact & Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| [Risk description] | High/Med/Low | High/Med/Low | [How to mitigate] |

**Performance implications:** [Any latency, throughput, or storage impact]  
**Security implications:** [Auth, input validation, data exposure concerns]  
**Backwards compatibility:** [Breaking changes? Migration needed?]

---

### 10. Implementation Sequence

Ordered steps that map to openspec tasks:

1. [Step 1 — what gets built first and why]
2. [Step 2]
3. [Step 3]

Each step should be independently deployable or at minimum independently testable.
```
